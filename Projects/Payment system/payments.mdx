**Problem**

Design a system that supports payments through Credit Card, PayPal, and Digital Wallet.
Each payment method should implement `pay(amount)` and `refund(transaction_id)`.

### A simple factory

This is the simpler solution that violates SOLID but it's the intuitive one so I must start here.

```text

|   CheckoutService   | ----------> |           PaymentFactory           |
|      (Client)       |             +------------------------------------+
+---------------------+             | + create(method): PaymentProcessor |
           |                        +------------------------------------+
           | uses                                     |
           |                                          | creates
           |      +-----------------------------+     |
           +----> |        <<Abstract>>         | <---+
                  |      PaymentProcessor       |
                  +-----------------------------+
                  | + pay(amount)               |
                  | + refund(transaction_id)    |
                  +-----------------------------+
                                 ^
                                 | inherits
           +---------------------+----------------------+
           |                     |                      |
+---------------------+ +-----------------+ +----------------------+
|  CreditCardPayment  | |  PayPalPayment  | | DigitalWalletPayment |
+---------------------+ +-----------------+ +----------------------+
| + pay(amount)       | | + pay(amount)   | | + pay(amount)        |
| + refund(tx_id)     | | + refund(tx_id) | | + refund(tx_id)      |
```

Now try to verify SOLID. The assumption is that the factory here will have an if casing to branch on what object to make.

Summarising ( for actual knowledge )

- go for simple factory first
- the whole thing is on "creation", it's a creational pattern after all. Selection on ui is not at all relevant here but in an actual app would pe, which is why you almost always know the full set of type unless you are building a library
- 100% closure is a myth, all we can do is move things as high as possible aka to the composition root

| Owner            | Maintains                                         | Decides                                                             |
| ---------------- | ------------------------------------------------- | ------------------------------------------------------------------- |
| Checkout         | `processOrder()`                                  | What order to charge and when to mark it paid                       |
| Payment platform | `PaymentFactory`, `execPayment()`, `execRefund()` | What validation, logging, and refund checks apply to every provider |
| PayPal team      | `PayPalFactory`, `PayPalProcessor`                | How to build the processor and how to talk to PayPal                |

Note that each owner is a level of "decoupling", you could have the checkout and payment platfomr merged but it's possible to have them separate.

### Practice

- **Goal:** Core checkout platform where external teams plug in providers implementing `pay(amount) -> tx_id` and `refund(tx_id)`.
- **Providers:** Card (`api_key`, `fee_rate`), PayPal (`merchant_email`), Wallet (`WalletAccount` with balance checks).
- **Constraints:** Unbypassable validation & double-refund guardrails; zero core edits when adding a new provider; `process_order()` stays decoupled; no untyped `dict`s.
- **Drills:** Add a 4th provider, mock-test `process_order()`, defend Factory Method vs. typed `match` vs. Strategy.

* Why use Factory Method instead of a Simple Factory or plain dict?
  - It hides divergent constructor dependencies (API keys, DB pools) behind a uniform interface and centralizes shared workflow logic (validation, refund tracking) in the base factory.
* Doesn't mapping user input (e.g., `"paypal"`) to a concrete factory still violate Open/Closed?
  - 100% closure is a myth; aim for strategic closure by pushing the mapping to the Composition Root (edge of the app) so core logic stays untouched, or use auto-discovery.
* Why is `pay(amount, details: dict)` a trap, and how do you avoid it?
  - A raw `dict` loses static typing and causes runtime `KeyError`s; use typed dataclasses in a Union with `match` and `assert_never` so the type checker catches missing cases.
* If a typed `match` block is just a Simple Factory, when is classic Factory Method actually needed?
  - When you have an open set of types—like a library or core platform where external teams plug in new implementations without modifying your code.
* Why pass a `PaymentFactory` instead of an already-built `PaymentProcessor` (like Strategy)?
  - Only when you need lazy creation, fresh instances per call/retry, or enforced base-class workflow guardrails; otherwise, simplify and pass the `PaymentProcessor` directly.
    - factory is what say I use and what I own, if I add just use processors then I don't have a single centralised place where I can put guardrails or tracking related common code. I don't want people to be using the payment processor without my wrapper.

### Followup to Abstract Factory

Now say every payment needs a provider specific `WebhookVerifier` class.

- what is verifier though?
  - the payment apis generally are async, they'll ack and then just respond on the verified webhook later via a POST.
  - Now the endpoint is public and anyone can hit it so what we need instead is some cryptographic proof that it's not some random person duping the POST.
  - The payment provider signs the payload with their priv key and I use their public key to verify that it indeed was the provider.
  - The verifier payloads are coupled to the provider here.

How do I statically make it so that the verifiers and providers are coupled and we never accidentally mix it?

- at the start from the verifier it's all just bytes
- add a common webhook response type => independent of what verifier it is, finally we reach this type
- naturally you need an abstract verifier that can map bytes to this response above.
- the provider specific impls need to satisfy that abstract requirement I just added.

Now at this stage we have two parallel lines of factories.

- `StripeProcessor(PaymentProcessor)` and a `StripeWebhookVerifier(WebhookVerifier)`, this would be same for `Paypal`
- note how the Stripe is related for the two objects, so in that sense they are coupled.

What abstract factory buys me is a guarantee of a matching family, I can never mix up different processors and verifiers.

```python
class PaymentGatewayFactory(ABC):
    @abstractmethod
    def create_processor(self) -> PaymentProcessor: ...

    @abstractmethod
    def create_verifier(self) -> WebhookVerifier: ...
```

The way this is done is that the factory that we made earlier `PaypalFactory(PaymentFactory)` now instead inherits a more composite type ( instead `PaymentFactory` which won't exist anymore ).

Something like

```python
class StripeFactory(PaymentGatewayFactory):
    def __init__(self, api_key: str, webhook_secret: str) -> None:
        self._api_key = api_key
        self._webhook_secret = webhook_secret

    def create_processor(self) -> PaymentProcessor:
        return StripeProcessor(self._api_key)

    def create_verifier(self) -> WebhookVerifier:
        return StripeWebhookVerifier(self._webhook_secret)
```

So anyone's operating with a `PaymentGatewayFactory` can't possibly mix the types up.

> in short this is just "boxing" related types together, nothing too remarkable I would say

But what if they mix it up at the boxing itself? What the argument goes like is that at $N$ places if we work with `PaymentGatewayFactory` as a box then we can't mess up those $N$, if at the construction level we mix things up, that can be a problem but what we get is error surface reduction from $N$ callers to just $1$.

### Practice

A similar set of questions but look for the terms here, you want those.

- Why use Abstract Factory instead of passing `PaymentProcessor` and `WebhookVerifier` separately?
  - It enforces a family invariant (no `StripeProcessor` + `PayPalVerifier` mix-ups) and shrinks the wiring bug surface from N callers down to 1 single-owner factory.
- How does Abstract Factory behave under Open/Closed for a new provider (Adyen) vs. a new product (`FraudChecker`)?
  - Asymmetric: a new family (Adyen) needs 0 edits to existing code, while a new product breaks the abstract factory and every implementer is needed to add that a that's a breaking change on interface ( whichever interface we chose to break - factory or processor )
- What if a provider (e.g., Cash-on-Delivery) has no webhooks—what's the trap with a No-Op or throwing verifier, and what's the fix?
  - A No-Op verifier is a silent security hole ( everything gets verified on an accidental misuse ) and throwing violates LSP; apply ISP by splitting into `PaymentFactory` (`create_processor`) and `AsyncPaymentGatewayFactory` (`+ create_verifier`).
- When is a pre-built bundle (`PaymentGateway(processor, verifier)`) better than a full Abstract Factory?
  - Use a pre-built bundle when components are stateless and cheap as you need to create the objects and have them survive through the lifetime of the app; use Abstract Factory only when you need fresh **per-request instances**, **lazy creation**, or **team-encapsulated assembly** ( same as the factory case )
- How do Factory Method and Abstract Factory differ, and how do they relate in code?
  - Factory Method decouples creating 1 supertype (typically via inheritance), while Abstract Factory clubs semantically coupled variants into one compatible family (via composition) and is literally built out of Factory Methods.

### Making a good API => Builder and Fluent

Both these are more like suggestions on how you build a nice internal DSL.
For this one say I want to make a data object `PaymentRequest`. One can live with a dict but that's won't be a good life.

Has the usual fluff liek mandatory fields/optional fields + validations on those, especially **cross field validations**.

- builder
  - cross field validations need things to be populated
  - object has "setters" which just sets things. Even if the validation is not cross field we don't throw here
  - finally when `set_one_field`, `set_whatever_other_field` etc are all done, I call `build` which will return me the object
  - the class that allows me to do so I would call as `PaymentRequestBuilder`
    - ctor for the fclass allows to set some default which I can use as bluepring to make objects with certain fields instead of doing set all over again.
- fluent
  - ctors and build remains the same
  - this is just chaining, each set, returns the object with the field set. Again no validations at the `with_x` or
    `with_whatever` layer
- merged builder
  - if the different types of default args that you need to set are really common, just add those to the builder itself.
